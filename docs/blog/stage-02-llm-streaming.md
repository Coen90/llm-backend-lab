# 에이전트 백엔드: 02. 답변 스트리밍과 생성 중단

[지난 단계](./stage-01-llm-serving.md)에서는 질문을 받아 완성된 답변을 반환하는 API를 만들었다. 이번에는 생성된 부분부터 스트리밍으로 전달하고 사용자가 원하면 생성을 중단할 수 있도록 확장했다. 구현하면서는 답변을 어떻게 보낼지보다 **이미 응답을 보내는 중에 작업을 어떻게 끝낼지**를 더 많이 고민했다.

## 1. 목표와 목적

### 완성된 답변을 기다리는 불편함

기존 API에서는 답변이 길어질수록 아무 내용도 보지 못한 채 기다려야 했다. 생성된 부분부터 읽을 수 있게 하고 싶었다. 스트리밍이 모델의 전체 생성 시간을 줄여주지는 않지만 답변이 끝나기 전에 내용을 확인할 수는 있다.

### 이번에 만들 기능: 스트리밍과 생성 중단

`POST /chat/stream`으로 답변을 조금씩 전달하고 `POST /chat/streams/:id/stop`으로 진행 중인 생성을 멈추도록 했다. 기존 `POST /chat`도 그대로 사용할 수 있다.

이번 목적은 요청이 진행되는 동안 데이터를 전달하고 완료·실패·사용자 중단에 맞춰 작업을 마무리하는 경험을 쌓는 것이다.

## 2. 무엇을 만들었나

Go와 Gin, 직접 구현한 OpenAI HTTP Client를 유지했다. 모델은 `gpt-5-nano`를 사용하고 Responses API 요청에 `stream: true`를 추가했다. 전체 코드는 [Stage 02 브랜치](https://github.com/Coen90/llm-backend-lab/tree/feature/stage-02-llm-streaming)에 있다.

### 스트리밍 API의 요청과 응답

`-N`으로 curl의 출력 버퍼링을 끄면 도착한 내용을 바로 확인할 수 있다.

```sh
curl -N http://127.0.0.1:8080/chat/stream \
  -H 'Content-Type: application/json' \
  -d '{"message":"Go의 context 역할을 예시와 함께 자세히 설명해줘."}'
```

응답은 SSE 이벤트로 전달한다. `event`는 이벤트 이름, `data`는 JSON 내용이다. 아래 텍스트와 ID, 사용량은 예시다.

```text
event: started
data: {"stream_id":"EXAMPLE_STREAM_ID"}

event: delta
data: {"text":"Go의 context는 작업의 "}

event: delta
data: {"text":"취소와 시간 제한을"}

event: delta
data: {"text":" 전달합니다."}

event: done
data: {"usage":{"input_tokens":20,"output_tokens":30,"total_tokens":50}}

```

`started`에서 작업 ID를 받고 여러 번 도착하는 `delta`의 텍스트를 순서대로 이어 붙인다. 정상 완료하면 `done`으로 최종 사용량을 전달한다.

### 생성 중단 API의 요청과 응답

스트리밍을 받는 터미널은 열어둔 채 다른 터미널에서 요청한다. `STREAM_ID`에는 `started`에서 받은 실제 값을 넣는다.

```sh
curl -i -X POST http://127.0.0.1:8080/chat/streams/STREAM_ID/stop
```

중단을 접수하면 HTTP 202와 `{"status":"stop_requested"}`를 반환한다. 원래 스트리밍 연결에서는 아래 이벤트를 보낸 뒤 응답을 끝낸다. 이미 끝났거나 존재하지 않는 작업에는 HTTP 404를 반환한다.

```text
event: started
data: {"stream_id":"EXAMPLE_STREAM_ID"}

event: delta
data: {"text":"Go의 context는 작업의 "}

event: user_cancelled
data: {"message":"사용자가 답변 생성을 중단했습니다."}

```

## 3. 어떻게 동작하나

### 모델의 텍스트가 사용자에게 전달되는 흐름

```text
사용자 질문 → Handler의 입력 검증 → started 전송 → OpenAI 호출
OpenAI 텍스트 → Client가 이벤트 해석 → 콜백 → Handler가 delta 전송·Flush
```

Client는 도착한 이벤트에서 텍스트를 꺼내고 Handler는 그 텍스트를 SSE로 보낸다. 답변 전체를 모아서 기다리지 않는다.

### Context로 모델 호출만 중단하는 흐름

```text
중단 요청 → 작업 ID로 취소 함수 찾기 → 모델 호출용 Context 취소
         → 외부 HTTP 요청 종료 → 원래 연결로 user_cancelled 전송
```

중단 안내를 보내려면 사용자 연결은 살아 있어야 한다. 그래서 사용자 요청의 Context 아래에 모델 호출용 Context를 만들고 중단 API에서는 자식만 취소한다. 사용자가 연결 자체를 닫으면 부모와 자식이 함께 취소되며 안내는 보내지 않는다.

### 정상 완료·오류·사용자 중단의 구분

정상 완료는 `done`, 모델 호출 실패나 미완성 응답은 `error`, 중단 요청으로 끝난 경우는 `user_cancelled`로 구분한다. 연결이 끊겨 마지막 이벤트를 받지 못했다면 정상 완료로 판단하지 않는다.

## 4. 구현하면서 고민한 것

### 왜 SSE를 선택했나

질문을 한 번 보낸 뒤 서버에서 생성하는 답변을 계속 받으면 됐다. 답변을 받는 동안 데이터를 양방향으로 계속 주고받을 필요는 없었다. 생성 중단도 별도 HTTP 요청으로 표현할 수 있어 SSE로 충분하다고 판단했다.

OpenAI도 Responses API의 스트리밍에 SSE를 사용한다. 직접 HTTP로 호출하며 응답 형식을 배우던 흐름을 이어갈 수 있었다. 사용자에게 보내는 이벤트는 Gin의 `SSEvent`와 `Flush`로 처리했다. [OpenAI 스트리밍 문서](https://developers.openai.com/api/docs/guides/streaming-responses)

이벤트를 설계하면서는 **첫 텍스트가 나오기 전에도 중단할 수 있어야 할까**를 고민했다. 모델을 기다리는 동안에도 사용자의 마음이 바뀔 수 있으므로 호출 전에 `started`로 작업 ID를 보내기로 했다.

대신 HTTP 200을 먼저 보낸 뒤에는 모델 호출이 실패해도 상태 코드를 바꿀 수 없다. 그래서 입력 오류는 스트림 시작 전에 HTTP 400으로 반환하고 시작 이후의 실패는 `error` 이벤트로 알린다. 이 API에서는 HTTP 200만 보고 답변이 성공했다고 판단할 수 없다.

### 왜 goroutine과 channel 대신 콜백을 사용했나

읽기와 보내기를 별도의 goroutine으로 나누는 방법도 있다. 하지만 현재 한 요청 안에서 필요한 순서는 단순했다. 이벤트를 읽고 텍스트를 보내고 다음 이벤트를 읽으면 됐다.

별도의 goroutine과 channel을 추가하면 읽는 쪽과 보내는 쪽을 연결하는 것 외에도 오류 전달과 종료 시점을 관리해야 한다. 이번에는 콜백으로 순서를 이어가고 전송 중 오류가 나면 콜백이 오류를 반환해 읽기도 끝내도록 했다. 이 방식이 코드를 이해하고 종료 경로를 확인하기 쉬웠다.

다만 사용자에게 보내는 작업이 느리면 다음 모델 이벤트를 읽는 것도 늦어진다. 지금은 흐름을 단순하게 유지하고 느린 연결을 처리할 때 쓰기 시간 제한이나 큐가 필요한지 다시 판단하려고 한다.

### 완료와 중단이 동시에 발생하면 무엇을 우선할까

모델이 답변을 마치는 순간에도 중단 요청이 들어올 수 있다. 중단 API를 추가하면서 이 경우를 어떻게 처리할지 생각해야 했다. 중단 요청에는 202를 반환했는데 원래 스트림에서는 `done`을 보내면, 사용하는 쪽은 어느 결과를 기준으로 삼아야 할지 애매해진다.

그래서 **중단 요청 접수와 완료 정리 중 먼저 처리된 쪽을 기준으로 삼았다.** 중단이 먼저 접수되면 `user_cancelled`로 끝낸다. 완료 정리가 먼저 끝나 작업이 제거됐다면 기존 결과를 유지하고 뒤늦은 중단 요청에는 404를 반환한다.

이 순서는 작업을 보관하는 map을 같은 Mutex로 보호해 정한다. 중단 API는 취소 신호만 전달하고 종료 이벤트는 원래 스트리밍 Handler 한 곳에서 선택해 보낸다. 완료와 중단이 겹쳤을 때 이 기준대로 처리되는지도 테스트로 확인했다.
